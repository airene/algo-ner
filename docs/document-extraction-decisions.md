# 文档字段抽取技术决策

本文记录 `rag-ner` 后续文档字段抽取能力的已确认结论，供不同开发机器恢复上下文。
更新时间：2026-08-02。

## 目标与边界

目标是在现有中文 NER 服务上增加文档字段解析能力。输入可能来自学校、政府和其他行政
单位，也可能是会议纪要、报告等非通知文档，不能把学校通知模板当作唯一场景。

需要解析的核心字段为：

- `title`：文档主标题，不是红头名称、文号或页眉。
- `published_at`：实际发文、签发或落款日期，不是正文中的会议日期、截止日期等。
- `issuing_organization`：实际发布或落款单位，不是正文中被提及的任意机构。
- `request`：要求接收方执行的内容；没有明确要求的文档应返回空值。一个文档可能包含
  多段要求，最终返回单值还是列表要在参考 TexSmart 实现后确定。

所有非空结果都必须能够映射回原文位置，不能生成、概括或改写原文不存在的内容。

## 已确认的模型路线

采用“NER 提供实体候选，工程代码进行文档结构和字段角色判断”的路线，不使用 LLM 直接
生成字段结果。

当前生产模型保持为：

```text
iic/nlp_raner_named-entity-recognition_chinese-base-generic
```

RaNER 只提供 `PER`、`ORG`、`LOC`、`GPE` 四类通用实体。它可以为发文单位等字段提供
候选，但不能直接判断字段角色；标题、发布日期和请求也不是当前 RaNER 原生支持的实体
类型。

后续工程层预计包括：

```text
OCR 或纯文本
  -> 保留原文位置的文本结构解析
  -> RaNER 实体候选
  -> 日期等补充候选
  -> 标题、发布日期、发文单位、请求的角色判定
  -> 原文位置与置信度校验
```

日期表达式可以用于发现和解析日期候选，但不能将遇到的第一个日期直接作为发布日期。
同理，机构 NER 结果只是候选，不能把正文中的任意机构直接作为发文单位。字段选择必须
结合候选上下文、所在段落、页面区域和文档结构。

## 已排除的方案

### Rex-UniNLU

`iic/nlp_deberta_rex-uninlu_chinese-base` 已经排除：

- 零样本实测不能稳定区分标题、发布日期、发文单位和请求。
- 工程源码、依赖、测试和 README 中均没有 Rex-UniNLU 引用。
- 本机正式缓存、临时缓存及下载锁已经删除。

不要在后续机器上重新下载或接入该模型，除非重新作出技术决策。

### LLM

LLM 能够解决通用文档理解，但这是已知方案，不是本项目当前要验证的路线。本项目优先
复用已有 TexSmart 生产经验，采用 NER 加工程解析。此前下载的 Qwen 本地模型仅是实验
缓存，不是工程依赖，也不会被服务加载。

## OCR 输入约定

### NER 接口

现有 `POST /v1/ner` 只需要纯文本，返回相对于输入文本的字符级 `start`、`end` 和
`span`。当前单次请求最多 480 个字符，完整文档不能直接作为一次 NER 请求发送。

### 文档解析接口

后续文档解析器应当同时考虑两种输入：

1. 纯文本降级输入：必须保留正确的换行、段落和阅读顺序。
2. 结构化 OCR 输入：推荐用于扫描件、红头文件、多栏排版和页眉页脚较多的文档。

结构化 OCR 至少保留：

- 页码及页面宽高；
- 行级文本；
- 行级边界框 `bbox`；
- 阅读顺序；
- OCR 置信度。

字级坐标不是第一版的必需项，行级坐标通常足够。建议的草案结构如下，最终以现有 OCR
工程和 TexSmart 参考代码的实际契约为准：

```json
{
  "pages": [
    {
      "page": 1,
      "width": 2480,
      "height": 3508,
      "lines": [
        {
          "text": "关于做好2026届毕业生离校工作的通知",
          "bbox": [320, 620, 2160, 710],
          "confidence": 0.98,
          "order": 4
        }
      ]
    }
  ]
}
```

文档解析器应负责从 OCR 行构建一份规范化全文、对全文分块调用 NER，并把分块内的字符
位置映射回全文和 OCR 行。不要把分块和位置合并责任分散给每个调用方。

## 当前工程状态

目前工程只实现：

- `POST /v1/ner`；
- `GET /healthz` 和 `GET /readyz`；
- macOS Apple Silicon CPU 与 Debian 13/Tesla T4 CUDA 12.9 两套运行环境；
- 本地缓存加载、启动预热、并发限制和 NER 输出位置校验。

文档字段解析器和对应 HTTP 接口尚未实现。

`tests/test_school_notice_extraction.py` 当前是一份待实现规格：测试输入已去掉人为添加的
“发布时间：”和“发文单位：”标签，但测试内的临时正则提取器仍依赖这些标签。因此当前
完整测试结果为 `15 passed, 1 failed`。这个失败不是模型或运行环境故障；在生产解析器
实现后，应删除测试文件内的提取实现，改为调用生产代码，并恢复全量测试通过。

## 等待的 TexSmart 参考代码

用户后续会提供之前生产项目中的 TexSmart 方案代码。拿到代码后先审查以下内容，再冻结
接口和开始实现：

- TexSmart 接收纯文本还是带位置的 OCR 结果；
- 使用了哪些实体类型、置信度和字符位置；
- 长文如何分块以及如何恢复全文位置；
- 标题、日期、发文单位和请求分别如何生成候选、评分及消歧；
- 多个发文单位、多个请求和字段缺失如何表达；
- 哪些逻辑是通用规则，哪些依赖特定客户或文种模板。

学校通知测试只是一个回归样例。至少还要增加行政通知、联合发文、包含多个日期和机构的
困难样例，以及没有明确请求的非通知文档。

## 实现验收条件

- 字段值与其位置能够准确还原到原文。
- 正文日期不会被误判为发布日期。
- 被提及机构不会被误判为发文单位。
- 非通知文档可以返回空请求，不强行套用通知模板。
- 长文分块后的位置仍相对于完整原文。
- 学校通知、行政单位文档和非通知文档均有生产代码级回归测试。
- macOS CPU 和 Linux T4 均完成真实模型验证，并记录耗时和内存占用。
